## Зачем это важно для DOLG

Архив показывает полный путь инженерной работы: от постановки задачи и требований до схемы, расчетов, проверки, производства, экономической оценки и ремонта. Для DOLG это полезнее обычного сравнения с CAD: сайт можно позиционировать как среду, которая ведет проектный сеанс через реальные инженерные этапы.

Главная мысль: DOLG должен не только рисовать схему и считать параметры, а хранить доказательства инженерного решения: требования, схему, расчеты, DRC/ERC, измерения, BOM, историю действий, отчет и замечания.

## Бинарные и CAD-артефакты

Дополнительно просмотрены сигнатуры и извлекаемые данные из бинарных/полубинарных файлов:

- `.vsd` и `.doc`
  - формат: OLE Compound File;
  - извлекаются потоки `SummaryInformation`, `DocumentSummaryInformation`, `VisioDocument`, `WordDocument`;
  - для Visio можно получать метаданные автора/приложения и факт наличия `VisioDocument`;
  - для старых Word-файлов можно получать число страниц/слов, автора, приложение и встроенные OLE-объекты.
- `.dwg`
  - формат AutoCAD DWG;
  - найдено 50 файлов `AC1032` и 4 файла `AC1024`;
  - полноценный разбор лучше делать через конвертацию DWG -> DXF, потому что DWG закрытый бинарный формат.
- `.dxf`
  - часть файлов читается как текстовый DXF;
  - примеры из P-CAD имеют `AC1009`, слои `Board`, `Top`, `Bottom`, сущности `INSERT` и `POLYLINE`;
  - часть DXF из Visio содержит нестандартные управляющие символы и требует tolerant-parser/очистки перед чтением.
- `.pcb` и `.sch`
  - формат P-CAD 2006 Binary;
  - из бинарных файлов извлекаются полезные строки: версия P-CAD, тип документа, слои, clearance rules, названия стилей, sheet;
  - полное восстановление схемы лучше делать не напрямую из binary, а через `.net`, `.drc`, `.erc`, `.dxf` и экспорт P-CAD.
- `.ms14`
  - формат Multisim compressed workbook;
  - сигнатура `MSMCompressedElectronicsWorkbenchXML`;
  - напрямую видна только сигнатура и фрагменты сжатого содержимого, для полного извлечения нужен отдельный декомпрессор/конвертер Multisim.

Вывод: бинарные файлы тоже полезны для обучения, но их нельзя сразу "скормить" модели как текст. Правильный путь - сделать слой нормализации:

`raw file -> metadata -> extracted entities -> normalized engineering facts -> review/fault/learning dataset`

Например:

- из DXF: слои, блоки, полилинии, текст, размеры;
- из DRC/ERC: тип ошибки, координаты, слои, сети, выводы;
- из P-CAD netlist: компоненты, корпуса, part numbers, соединения;
- из Visio/DOC: тип документа, структура, авторство, встроенные объекты;
- из DWG/MS14: сначала конвертация или внешнее извлечение, затем тот же нормализатор.

## Детали, которые стоит перенести в продукт

### 1. Сеанс проектирования

В старых материалах проект всегда проходит цепочку:

1. Назначение устройства.
2. Анализ методов и аналогов.
3. Функциональная схема.
4. Выбор элементной базы.
5. Принципиальная схема.
6. Расчеты.
7. Конструкция и печатная плата.
8. Технология сборки.
9. Испытания.
10. Карта отказов и ремонт.
11. Экономика.
12. Безопасность.

Для DOLG это подтверждает идею `SchematicProject` как контейнера сеанса проектирования. В проектном кабинете должны быть не только схема и BOM, но и история действий, версии, результаты проверок, измерения, отчет и комментарии.

### 2. Надежность и derating

В `ПЗ Буряко.pdf` расчет надежности строится вокруг:

- интенсивности отказов элементов;
- количества элементов каждого типа;
- коэффициентов нагрузки и температуры;
- среднего времени наработки на отказ;
- вероятности безотказной работы.

Для DOLG из этого получается отдельный модуль:

- `ReliabilityCalculator`;
- расчет `failure_rate_total`, `MTBF`, `P(t)`;
- review findings по слабому запасу;
- учебное задание по расчету надежности простого узла;
- блок в отчете проекта: "Надежность и запас".

### 3. Входной контроль и технологичность

В технологическом процессе отмечены:

- получение комплектующих по комплектовочной карте;
- входной контроль ИМС, ПП, резисторов и разъемов;
- проверка маркировки, ключа первого вывода, трещин, сколов, вздутий, расслоений;
- очистка платы;
- формовка выводов;
- контроль качества пайки;
- повторная пайка только при необходимости.

Для DOLG это можно оформить как `Manufacturing Readiness`:

- проверка полноты BOM;
- наличие корпуса/package;
- наличие datasheet;
- наличие footprints/CAD-моделей;
- предупреждение о неуказанном монтаже;
- checklist для сборки и защиты.

### 4. Испытания и эталонные измерения

В документе по металлодетектору рабочая проверка выполняется на стенде, а дефекты ищутся осциллографом через сравнение временных диаграмм в контрольных точках с эталонными.

Это напрямую усиливает DOLG:

- в `ProjectMeasurement` добавить тип "reference waveform";
- в лаборатории показывать expected vs measured;
- в review учитывать не только факт симуляции, но и совпадение с эталоном;
- в обучении сделать задания "измерить точку и сравнить с эталоном".

### 5. Карта отказов и диагностика

В старом процессе при отказе фиксируются:

- выявленные причины;
- влияние отказа на другие элементы;
- дата и причина ремонта;
- замененные элементы;
- повторная проверка после устранения дефекта.

Для DOLG это можно превратить в:

- `FaultScenario`;
- `ProjectFaultReport`;
- "симптом -> причина -> проверка -> действие";
- учебный track "Диагностика простых схем";
- AI-команду "составь план поиска неисправности".

### 6. P-CAD DRC/ERC как материал для CAD-import

Файл `Untitled1.drc` дает реальные типы ошибок:

- `outside board outline`;
- `shorted to Net`;
- `connected to uncommitted pin`;
- clearance/component violations.

Это хороший первый формат для импортера внешних отчетов:

- парсер DRC/ERC отчета;
- перевод ошибок на русский;
- маппинг в `ProjectReview.findings`;
- severity по типу ошибки;
- evidence с координатами и названием сетей;
- демо "внешний CAD -> DOLG review".

### 7. Бинарный пайплайн для локальной нейронки

Для будущей локальной нейронки архив можно использовать не как хаотичный набор файлов, а как обучающий корпус инженерного процесса:

- `document_summary` - тип документа, тема, разделы, ключевые термины;
- `cad_artifact` - формат, версия, слои, сущности, элементы;
- `check_report` - ошибки DRC/ERC, severity, evidence, координаты;
- `bom_artifact` - перечень элементов, цены, корпуса, количество;
- `process_step` - требование, расчет, проверка, сборка, испытание, ремонт;
- `fault_case` - симптом, причина, способ проверки, действие.

Такой датасет лучше подходит для DOLG, чем "чатовая" дообучалка. Модель должна не переписывать ответы из воздуха, а ранжировать и подсказывать поверх структурированных фактов.

### 7. Трассировка требований

В лабораторных по требованиям есть связка:

- `SYS.*` системное требование;
- `PROG.*` программное требование;
- родительское требование;
- дочерние требования;
- проверка полноты и непротиворечивости.

Для диплома и кода это можно использовать как `RequirementsTrace`:

- требование -> модуль -> API/view/service -> тест -> демо-сценарий;
- помогает показать, что проект не просто "написан", а инженерно спроектирован;
- можно добавить lightweight markdown/JSON-матрицу без тяжелой БД.

### 8. Экономика и BOM

В старом дипломе стоимость изделия считается через:

- сырье и материалы;
- покупные комплектующие;
- зарплату;
- переменные и постоянные издержки;
- производственную и полную себестоимость;
- прибыль;
- итоговую цену.

Для DOLG это усиливает коммерческую часть:

- BOM cost breakdown;
- закупочная цена;
- стоимость сборки;
- резерв/наценка;
- сравнение вариантов BOM;
- экспорт "экономическая оценка проекта".

### 9. Безопасность и область применимости

Документ отдельно фиксирует:

- требования электробезопасности;
- исправный инструмент;
- заземление металлических корпусов;
- работу минимум двумя людьми при экспериментальных испытаниях;
- риски при невозможности заземления корпуса.

Для DOLG это поддерживает текущий `Design Validity Guard`:

- результат симуляции может существовать, но режим может быть вне допустимой области;
- предупреждения по напряжению, току, мощности, температуре;
- предупреждение "последний контроль остается за человеком".

## Что добавить в DOLG по итогам чтения

### Быстро и полезно

1. Добавить в Engineering Review раздел "Надежность и запас".
2. Добавить в project dashboard блок "История сеанса" уже реализованной модели `ProjectEvent`.
3. Добавить в AI-панель команду "план поиска неисправности".
4. Добавить переводчик/маппинг DRC/ERC findings на русский.
5. Добавить демо-импорт P-CAD DRC отчета как внешний review input.
6. Добавить checklist "готовность к сборке": datasheet, корпус, BOM, footprint/model, ratings.

### Средний слой

1. `ReliabilityCalculator` с расчетом MTBF и вероятности безотказной работы.
2. `FaultScenario` и библиотека типовых симптомов.
3. `ReferenceMeasurement` или расширение `ProjectMeasurement` под эталонные точки.
4. `RequirementsTrace` в формате JSON/Markdown.
5. BOM economic report: комплектующие, сборка, запас, итоговая цена.

### Дальше

1. P-CAD netlist subset -> `scheme_data`.
2. DRC/ERC импорт не только из P-CAD, но и из KiCad/LTspice/других форматов.
3. Manufacturing readiness score.
4. Сравнение версий проекта: review до/после исправлений.
5. Нейронный deep-hint слой обучать не на "чате", а на структурных данных: scheme graph, DRC findings, measurements, BOM facts, fault reports.
