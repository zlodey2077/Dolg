## 1. Engineering Review V2 улучшения

### 1.1. Расширить DRC до 40+ правил из индустриальных источников (3-5 дней)

Сейчас 7 frontend-правил в `runQuickDRC` (GND, source, висячие порты, одиночные пины, ∥ batteries, LED без R, voltage rating). **Это смешно для CAD-программы.** Нужно набрать ~40-50 implementable правил из открытых источников.

#### Источники

| Источник | Лицензия | Сколько правил берём |
|---|---|---|
| **KiCad ERC** (`eeschema/erc.cpp`) | GPL — читаем, не копипастим | 15-20 (electrical rules) |
| **IPC-2221A** «Generic Standard on Printed Board Design» | Industry standard, описание открыто | 8-10 (clearance, trace, voltage) |
| **EAGLE .dru** format spec | Public | парсер на будущее (импорт rules-файлов) |
| **OpenSPICE checks** | GPL | 5-7 (DC convergence, floating nodes) |
| **Industry practice** (datasheet typical ratings) | Public | 10-15 (BC547 Vceo, LED 20mA, electrolytic polarity) |

#### Категории правил (минимум 40 итого)

**A. Connectivity (10 правил)** — частично есть:

- ✅ A1. Нет GND
- ✅ A2. Нет источника питания
- ✅ A3. Висячий порт (открытый pin)
- ✅ A4. Одиночное соединение компонента
- A5. Floating net (узел без подключения к GND через любой путь)
- A6. Кратный GND с разными net'ами (исключая аналоговый/цифровой GND намеренно)
- A7. Wire crossing без junction-dot (визуальная двусмысленность)
- A8. Параллельные провода ближе 4px (визуально слипаются)
- A9. Висячий именованный net (label на проводе, который никуда не идёт)
- A10. Микро-сегмент wire'а < 5px (мусор от плохого роутинга)

**B. Source/Power (8 правил)** — частично:

- ✅ B1. Параллельные V-источники разного напряжения (КЗ)
- B2. Source → GND без резистора (КЗ через источник)
- B3. Параллельные source одного потенциала (предупреждение о шунте)
- B4. Источник без обратного провода к GND (open circuit)
- B5. Battery подключена обратной полярностью к нагрузке
- B6. Current source без замкнутой петли (нарушение Кирхгофа)
- B7. AC source без DC-bias компонента
- B8. Multiple sources с противоположными полярностями на одном net'е

**C. Polarized components (6 правил)** — почти нет:

- ✅ C1. LED без токоограничивающего резистора
- C2. LED обратной полярности (анод к минусу источника)
- C3. Electrolytic capacitor обратной полярностью (взрыв в реале)
- C4. Diode обратной полярностью в выпрямительной схеме
- C5. Transistor B/E/C перепутаны (heuristic)
- C6. Battery без декаплинг-конденсатора

**D. Component ratings (8 правил)** — частично:

- ✅ D1. |V| > rated voltage компонента (после симуляции)
- D2. I > rated current через резистор (P = I²R > P_max)
- D3. Capacitor над rated voltage (на DC + AC peak)
- D4. Transistor Vceo превышен
- D5. Diode reverse voltage > Vbrk
- D6. LED current > 20mA (нагрев)
- D7. Resistor power dissipation > rating (1/4W, 1/2W)
- D8. Inductor saturation current превышен

**E. Topology / good practices (10 правил)**:

- E1. RC-filter с пиками частот (резонанс не учтён)
- E2. Op-amp без feedback (open-loop недопустимо)
- E3. Op-amp с input out-of-range (rail-to-rail violation)
- E4. Digital input без pull-up/down (плавает)
- E5. Несимметричный делитель напряжения для AC (отсечение)
- E6. Кэп близкий к input (трактуется как фильтр vs декаплинг)
- E7. Trace width слишком узкая для тока (если PCB-режим)
- E8. Reset-pin без external pull-up
- E9. Crystal/oscillator без load-capacitors
- E10. Differential signal с непарной длиной проводников

#### Реализация

- **Конфиг:** `Dolg_APP/expert_rules/default_rules.json` — расширить с 8 до 40+ записей. Каждое правило:
  ```json
  {
    "id": "C2",
    "category": "polarized",
    "severity": "error",
    "title": "LED обратной полярности",
    "recommendation": "Анод (+) должен быть подключён к +V через резистор. Поменяйте местами выводы LED.",
    "detector": "detect_led_polarity",
    "source": "Industry / IPC-A-610",
    "tags": ["led", "polarity", "common-mistake"]
  }
  ```
- **Detectors:** `Dolg_APP/services/expert_detectors.py` — добавить 30+ функций `detect_<id>(scheme_data, graph)`.
- **Frontend mirror:** `runQuickDRC` — наиболее «дешёвые» проверки оставить в JS для instant feedback. Сложные (требующие симуляции) — только backend.
- **Группировка в UI:** Review-модалка показывает правила сгруппированными по категориям (A/B/C/D/E) с раскрытием.

#### Acceptance

- Для делителя напряжения с GND и source: 0 errors, может быть 1-2 info (например «декаплинг отсутствует» — opt-in).
- Для схемы с обратной LED + резистор 1Ω на 12В: 2 errors (C2 «обратная полярность», D7 «P=144Вт > rating»).

## 2. Симулятор улучшения

### 2.1. AC-анализ → Bode plot в scope (1-2 дня)

Сейчас AC-результат показывается **таблицей** в results-panel. Это бесполезно — никто не читает таблицу частот. Сделать визуализацию:

- В scope canvas (тот же который для TRAN) добавить режим «AC»:
  - X-ось: логарифмическая частота (Гц)
  - Y-ось верх: магнитуда (dB)
  - Y-ось низ: фаза (°)
- Сетка: 1 декада на 2 деления.
- 3dB cutoff отмечается вертикальной линией.
- Phase margin / gain margin в info-line.

**Acceptance:** RC-фильтр 1k+100nF → запустил AC sweep 10Гц..100кГц → видишь -3dB точку на 1.6кГц, slope -20dB/dec.

### 2.2. FFT в scope для TRAN (4-6 часов)

В scope-controls добавить **только в `<select>`** новый параметр режима — не новая кнопка. Сейчас `dolgLabScopeMode` нет, есть просто scope. Добавить state:

```
scope.mode: 'time' | 'fft'
```

В time-режиме (default) — current scope. В fft — берём points, делаем FFT, рисуем спектр X=частота, Y=амплитуда.

FFT через простую Cooley-Tukey radix-2 на JS (не нужны deps).

**Acceptance:** запусти TRAN с sine 1кГц → переключи на FFT → видишь пик на 1кГц.

### 2.3. Probe-помощник через ПКМ на проводе (4-6 часов)

В контекст-меню провода (`context-menu-wire`) добавить **существующий** пункт «Probe этот провод» (это **расширение** существующего dropdown — не новая кнопка в toolbar). При клике:
1. Имя net'а провода → новая запись в Probes-таб
2. После следующей симуляции в Probes показывается живое значение

Это уже частично есть в Properties → ⊕ Probe. Просто добавляем доступ через ПКМ.

### 2.4. Кэширование результатов симуляции (3-4 часа)

Хэш `JSON.stringify(circuit)` → ключ кэша. Если хэш совпадает с предыдущим вызовом — мгновенно отдать кэшированный результат. Кэш в-memory (Map), макс 10 записей.

**Acceptance:** после первого ▶ Запуск повторный запуск без изменений → 0мс «✓ из кэша».

### 2.5. Корректная обработка инженерных единиц (2-3 часа)

Проверить все поля Properties: «4.7k», «100u», «1n», «220p» должны парситься в SI. Сейчас `parseEngValue` есть, но не везде применяется. Аудит + фикс.

**Acceptance:** ввёл «4.7k» в R → сохранилось как 4700 → симуляция корректна.

### 2.6. Worker cancel-token (3-4 часа)

Сейчас при ▶ Запуск во время симуляции — старая запускается параллельно с новой → race condition. Добавить `_currentSimToken` — если новый запуск, старый прерывается.

**Минимум для защиты:** §2.1 + §2.3 + §2.5. Общее время: **11-16 часов** (~2 дня).

## 3. Постройка схем улучшения

### 3.1. Alignment guides при drag (1 день)

Когда юзер тащит компонент — рисуем синие пунктирные линии к X/Y координатам других компонентов в радиусе 60px:

```
       │
       │ ← synced X с R3
       │
[R1]   ↓
       [R2-dragging]
       
       [R3]
```

Snap-tolerance 6px к этим линиям. **Это улучшение существующего drag поведения, не новый UI.**

**Acceptance:** перетягиваю R2 рядом с R1 — видна вертикальная синяя линия — R2 snap к X(R1).

### 3.2. Snap к grid обязательный + finer grid option (4 часа)

Сейчас при перетаскивании компонент может оказаться на промежуточных координатах. Сделать snap **всегда**, размер grid — настраиваемый в hamburger «⚙ Вид»:
- Coarse: 20px
- Default: 10px
- Fine: 5px

Если зажат Shift — отключение snap.

### 3.3. Wire routing — фиксы из накопленного бэклога (1-2 дня)

Из `docs/SCHEMATIC_EDITOR_FIXES.md`:
- **Hit-detection:** расширить tolerance до `max(4, 6/zoom)` — на zoom out wire'ы попадаются проще
- **Wire drag целиком:** клик на середину провода (не Ctrl) → drag перемещает весь провод с его waypoints + resnap endpoints
- **Симплификация смягчить:** не съедать valid waypoints (юзер: «правило слишком жёсткое»)
- **Логирование:** `window._dolgDebugRoute = true` → console.debug с дампом pts

### 3.4. Inline net-label edit (3-4 часа)

Сейчас ПКМ → prompt'() для имени net'а. Это плохой UX. Сделать **двойной клик по проводу** → inline-input прямо на канвасе → ввёл «VCC» → Enter применяет.

Это улучшение существующего пути (через ПКМ → setWireNetLabel), без новой кнопки.

### 3.5. Группы и подсхемы (2-3 дня)

Выделить группу компонентов → ПКМ → «Группировать как subcircuit». Создаётся новый component-type «subcircuit» с pin'ами (внешние net'ы выходят на pin'ы). Двойной клик по subcircuit → открывается его внутренняя схема в отдельной вкладке.

**Это новый тип компонента, не новый UI** — добавление в ПКМ-меню (которое уже есть) + специальное поведение при двойном клике.

### 3.6. Template-палитра (2-3 дня)

Юзер выделил RC-фильтр → ПКМ → «Сохранить как шаблон» → даёт имя → шаблон сохраняется в `localStorage.dolg.templates[]`. В hamburger меню (внутри существующего) появляется подсекция «📋 Шаблоны» с сохранёнными.

Insert template → клик на канвас → шаблон вставляется со смещением.

### 3.7. Auto-route при move компонента (1 день)

Сейчас при move компонента waypoints проводов сбрасываются → проводы становятся прямыми. Это часто плохо если был careful routing. Сделать smart-mode:
- Если новая позиция близко к старой (< 50px) → waypoints сохранить
- Если далеко → пересчитать через `buildOrthogonalPath` с avoidance компонентов

### 3.8. Mirror компонента (2-3 часа)

ПКМ компонента → «Зеркалить горизонтально / вертикально». В существующее ПКМ-меню.

**Минимум для защиты:** §3.1 + §3.3 + §3.4. Общее время: **2-3 дня**.
