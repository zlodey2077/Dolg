## Правила работы (best practices)

- **Мультимодальный поиск информации.** Когда ищешь инфу в интернете — использовать НЕ
  только текст, но и другие модальности: **видео** (транскрипт через `yt_transcript` →
  конспект), доки библиотек (context7), при необходимости аудио/кадры. Текст — не
  единственный источник; видео часто отражает практику и «суть» лучше статьи.

### 1. Что такое деплой? (Kubernetes)
[видео, 13:00](https://www.youtube.com/watch?v=n5Yk-9hZgXw)

**TL;DR:** Деплой в K8s = набор правил поверх декларативного подхода (описываем *желаемое
состояние*, кластер сам приводит реальность к нему).

**4 столпа деплоя:**
- **Deployment** — образ/версия, число реплик, лимиты CPU/RAM.
- **ConfigMap** — настройки отдельно от кода (не пересобирать образ ради смены лог-уровня/URL).
- **Service** — стабильная точка входа (поды смертны, IP меняются); раскидывает трафик на живые поды внутри кластера.
- **Ingress** — «дверь снаружи внутрь»: домен → Service.

**Путь деплоя 2025:** код → Docker → манифесты (можно генерить ИИ, но *доверяй-но-проверяй*) →
**Helm** (шаблон + `values-dev/prod.yaml` вместо копий YAML) → **CI** собирает образ в registry →
**CD/GitOps (ArgoCD)**: CI делает git-commit в инфра-репо, ArgoCD изнутри кластера синхронизирует.

**GitOps плюсы:** снаружи в кластер не ходим (безопасно); source of truth = git; self-healing
(вернёт состояние из git); авто-откат, canary/blue-green.

**Грабли:** stateful (БД/очереди) в K8s — боль, лучше VM/managed; секреты — Vault/Sealed Secrets,
никогда в репо; мониторинг (Prometheus/Grafana) — часть деплоя.

**Релевантность DOLG:** дорожная карта *если* пойдём в оркестрацию. Принцип «конфиг отдельно
от кода» + секреты уже актуальны для `settings.py`/`.env`. Stateless-движки (SPICE/КОМПАС в
контейнере) — кандидаты в K8s; БД — нет.

### 2. Всё про Docker (best practices)
[видео, 19:00](https://www.youtube.com/watch?v=vBD4jzv0oJ0)

**TL;DR:** Идеальный образ стоит на трёх китах — **скорость, безопасность, надёжность**. 13 правил.

**Образ — минимальный:**
- **Alpine** (~5 МБ, musl libc — для Go/статиков; Python/C++ могут тормозить/ломаться) →
  **slim** (Debian без доков, но с glibc — безопасный дефолт для Python) → **distroless**
  (только рантайм+приложение, нет shell/пакетника — максимум безопасности, но не подебажить).
- **Не `latest`** — пинить конкретную версию (`node:18-alpine`) → детерминированная сборка байт-в-байт.
- **`.dockerignore`** — не слать демону `.git`/`node_modules`/логи (скорость + безопасность).

**Кэш слоёв (быстрая пересборка):**
- Образ = слои; меняется слой → все последующие пересобираются.
- **Отделять зависимости от кода**: сначала `COPY` манифестов (requirements.txt) + установка,
  потом `COPY` остального кода → слой зависимостей берётся из кэша при правке кода.
- **Объединять команды** в один слой (`RUN a && b && rm cache` через `&&` + `\`) — иначе удалённые
  файлы остаются «мёртвым грузом» внутри образа.
- `COPY` (не `ADD`) для локальных файлов; для скачивания — `RUN wget/curl`. `ADD` — антипаттерн.

**Мультистейдж** (главное!): билд-стейдж (компиляторы/SDK, ~1 ГБ) → финальный стейдж копирует
только артефакт в чистый alpine (~15 МБ). Быстро качается, безопаснее (нечем взламывать).
**BuildKit** — современный движок (граф зависимостей, параллельные стейджи, cache mount);
включать `DOCKER_BUILDKIT=1` на старых CI.

**Безопасность:**
- **Непривилегированный пользователь** (`USER appuser`) — иначе root в контейнере = root на хосте при побеге.
- **Build secrets** (`--mount=type=secret`, требует BuildKit) — не `ARG`/`ENV` (запекаются в `docker history`).

**Надёжность (сигналы/оркестратор):**
- **PID1 ловит сигналы**: запуск через `exec` (приложение становится PID1) или `tini` (Java/капризные)
  — иначе SIGTERM от оркестратора игнорится → SIGKILL → оборванные транзакции.
- **HEALTHCHECK** — иначе Docker судит «жив ли процесс», а не отвечает ли приложение (зомби-контейнер).
- **hadolint** — статический анализ Dockerfile в CI.

**Релевантность DOLG (прямо в наш `Dockerfile`/`deploy/`):**
- База: `python:3.x-slim` (не alpine — у нас numpy/scipy/torch на glibc), пинить версию.
- `COPY requirements*.txt` → `pip install` ПЕРЕД `COPY` кода (кэш зависимостей — у нас тяжёлые либы).
- Мультистейдж: собирать колёса/ассеты в билд-стейдже, в финал — только нужное.
- Непривилегированный USER (есть в security backlog), HEALTHCHECK на `/healthz` (у нас уже есть `health.py`!),
  `.dockerignore` (`.venv`, `.git`, `media`, `*.log`), hadolint в pre-commit.

### 3. NGINX
[видео, 13:41](https://www.youtube.com/watch?v=2dJvLXy5RSE)

**TL;DR:** nginx (Игорь Сысоев, Rambler, 2004) решил проблему **C10K** асинхронной event-driven
архитектурой — где Apache (процесс на соединение) умирал на 10k, nginx держит сотни тысяч.

**Архитектура:** master-процесс (читает конфиг, не обрабатывает запросы) + worker'ы (≈ числу ядер),
каждый асинхронно держит тысячи соединений (event loop). Reload конфига без простоя
(новые воркеры стартуют, старые доживают запросы).

**Что умеет:**
- **Статика** — отдаёт HTML/CSS/JS/картинки вне конкуренции.
- **Reverse proxy** (основная роль): SSL/TLS-терминация (бэкенд не возится с сертификатами),
  буферизация медленных клиентов, единая точка входа, маршрутизация по путям/доменам.
- **Балансировщик** (разные алгоритмы), **кэш ответов** бэкенда (1000 запросов из кэша, не дёргая бэк).
- Производительность: 8 ядер/16 ГБ → 50-100k rps статики, 10-50k rps reverse-proxy, до 2 млн соединений.

**Где не тянет:** частый reload на больших кластерах; статичный конфиг (правка файла + reload);
service mesh (mTLS между сервисами, трейсинг, ретраи) — это Istio/Envoy, не nginx. В K8s Ingress
на базе nginx → `deprecated` в пользу Gateway API (но работать будет ещё долго).

**Релевантность DOLG (у нас `deploy/nginx.conf`):**
- Мы используем nginx именно как reverse proxy перед Django/Daphne — ровно сценарий из видео.
- Actionable: SSL-терминация на nginx, отдача `static/`+`media/` напрямую nginx'ом (не Django),
  кэш статики, gzip/brotli, буферизация. Для нашего масштаба (один сервер) nginx — идеален,
  mesh/Envoy не нужны.

### 4. Всё про базы данных
[видео, 19:46](https://www.youtube.com/watch?v=ApyFWo1Qimg)

**TL;DR:** БД — единственный **stateful** компонент: «приложения — скот, БД — сердце». Универсальной
базы нет, инструмент подбирается под профиль нагрузки.

**Классы баз:**
- **Реляционные (Postgres/MySQL)** — деньги/заказы/строгая структура, гарантии **ACID**. Postgres = стандарт.
- **NoSQL (MongoDB)** — нет жёсткой схемы (каталог разнородных товаров, профили с вложенностью); JSON-доки,
  но прожорлива и сложнее в админинге.
- **In-memory (Redis/Memcached)** — микросекунды, кэш/сессии/счётчики; энергозависимо — *ускоритель, не хранилище*.
- **Колоночные (ClickHouse)** — миллиарды строк аналитики/логов, сжатие ×десятки; жрёт все ядра.
- Взрослая архитектура — гибрид: Postgres хранит, Redis кэширует, ClickHouse анализирует.

**Надёжность:**
- **SPOF** (один сервер) недопустим → **репликация** (master пишет, реплики копируют через журнал **WAL**
  — «сначала запиши в журнал»). Реплика проигрывает WAL и становится копией.
- **Синхронная** (ждёт реплику — банки/биллинг, ≥3 серверов) vs **асинхронная** (быстро, риск потерять
  последнюю запись — соцсети/блоги). Вечный компромисс скорость↔надёжность.
- **Failover** автоматом (не руками в 3 ночи): **Patroni** + распределённый арбитр (etcd/Consul) — лидер
  держит ключ с TTL, при смерти ключ протухает, реплики гонятся за лидерством, победитель → master + переезд VIP/DNS.
- **Репликация ≠ бэкап!** `DROP` реплицируется на все сервера за миллисекунды. От человеческой ошибки — только бэкап.
  - Логический (дамп в текст — просто, но медленно: 1 ТБ = часы/сутки) vs физический (копия файлов + архив WAL →
    **PITR**, восстановление на точку во времени «за секунду до того как Вася дропнул»).
  - **RPO** (сколько данных готовы потерять) и **RTO** (сколько лежим при восстановлении) — задаёт бизнес.

**БД в Kubernetes:** можно (2026), но с умом — НЕ `Deployment`, а `StatefulSet`, а лучше **операторы**
(сами делают Patroni/TLS/бэкапы). On-prem → операторы; облако → managed-сервис. Большой нагруженный
монолит-БД → лучше VM (предсказуемость); 500 мелких БД / БД-на-PR → Kubernetes-фабрика.

**Golden signals БД (мониторить, не CPU):** активные соединения (+ **PgBouncer** как пулер, не пускать
приложение в БД напрямую); диск IOPS/очередь; lag реплики; блокировки; **здоровье бэкапов** (алёрт на
возраст последнего успешного архива!).

**Релевантность DOLG (наш переход SQLite→Postgres):**
- Подтверждает выбор Postgres (ACID для заказов/оплаты Stripe). См. чек-лист postgres-миграции в памяти.
- Для production: настроить WAL-архивацию + физический бэкап с PITR (security backlog: «бэкапы»),
  алёрт на возраст бэкапа, PgBouncer при росте соединений.
- Реплика/Patroni — оверкилл для диплома (один сервер), но знать для защиты («как бы масштабировал»).
- Redis у нас уже есть в планах (кэш/Channels) — ровно роль «ускорителя».

### A. AutoCAD — основы и принцип работы
Видео: [Суть за 12 мин](https://www.youtube.com/watch?v=-3gBve13nvA) · [Принципы черчения — Меркулов](https://www.youtube.com/watch?v=mxnkkBODIXA) · [Как работать — AutoCAD-Просто.ру](https://www.youtube.com/watch?v=lhTPbI3hGc4)

**Принцип:** команды → их настройки → параметры → вывод на печать. Всё в миллиметрах.
- **Примитивы** (панель «Рисование»): отрезок, окружность, дуга, прямоугольник, полилиния (единый объект из сегментов), сплайн. Командная строка = гид: всегда читаем подсказку.
- **Построение:** клик первой точки → направление мышью → ввод числа → Enter. Замыкание по привязке.
- **Привязки (osnap, F3):** конечная/середина/центр/пересечение/продолжение — «магнит» к ключевым точкам (зелёный маркер). Настраиваются.
- **Орто (F8)** — строго гор/верт; **полярное отслеживание** — углы кратно N° (15/30/45…); **динамический ввод** — подсказки у курсора.
- **Редактирование:** copy/move/rotate/mirror (зеркало с удалением/без), trim (обрезка), **ручки (grips)** для правки/перемещения, Escape (отмена команды), Ctrl+Z, свойства (Ctrl+1).
- **Слои (layers):** цвет/тип линии/вкл-выкл/заморозка. «Сразу делать правильно» — редактирование потом в разы проще. Тип линии + **LTSCALE** (масштаб типов линий).
- **Зум:** колесо; 2×клик колесом = вписать всё (zoom extents); при упоре в лимит — команда `REGEN`.
- **Размеры:** linear/parallel/diameter/radial + **размерные стили** (глобальный масштаб увеличивает все размеры) + **аннотативность** (размеры видны в любом масштабе листа).
- **Печать/листы:** model → «DWG to PDF», формат, центрировать, масштаб; пространство **листа (layout)** + видовые экраны с масштабом вида (1:30 и т.п.).

### B. AutoCAD — массивы
Видео: [Прямоугольный массив — APROSVET](https://www.youtube.com/watch?v=T4EkOTHs5sQ) · [Массив по траектории — APROSVET](https://www.youtube.com/watch?v=_I6N-XLB9Mc)

**Массив** = N одинаковых элементов на равном расстоянии по закону. 3 вида: прямоугольный, круговой, по траектории.
- **Прямоугольный:** столбцы × строки, расстояние от базовой точки; +/− значения = направление осей; ручки для интерактива; базовая точка переназначается.
- **Ассоциативность (важная кнопка!):** ON → массив как единый объект: «редактировать источник» (правишь один → меняются все), «заменить элемент», «сбросить»; Ctrl+выбор отдельного → перенос/поворот/масштаб одного. OFF → отдельные примитивы. `Explode` (расчленить) разбивает массив/блок.
- **По траектории:** распределение вдоль кривой; «измерить» (фикс. шаг) vs «поделить» (фикс. число); выравнивание элементов по траектории; base point.

### C. AutoCAD — динамические блоки
Видео: [Динамические блоки (зеркало/полярный/видимость/массив) — Жирнова](https://www.youtube.com/watch?v=77Ope_OYDXI) · [Создание динам. блока (окно)](https://www.youtube.com/watch?v=uPBTa5KQnmU)

**Блок** = переиспользуемый объект; **динамический** = блок с параметрами + операциями (порядок: сначала параметр, потом операция на него).
- **Отражение (mirror):** оси отражения; ручки разносить, чтоб не накладывались.
- **Полярное растяжение:** «наборы параметров» ускоряют (параметр+операция одним набором).
- **Видимость (visibility states):** несколько вариантов графики в ОДНОМ блоке (одно-/двух-/трёхполюсный выключатель; **штампы основной надписи для разных листов**). Супер для библиотек УГО.
- **Линейный параметр + растяжение + «набор значений»:** стандартный ряд ширин (окно 1200/1500/2000) — растяжение прыгает по списку.
- **Атрибуты** (текстовые поля, напр. диаметр) + **извлечение данных** в таблицу/спецификацию (data extraction, связана с чертежом, авто-обновляется).

### D. КОМПАС — основы 3D
Видео: [За 5 минут — Шагинян](https://www.youtube.com/watch?v=buNGM7B2TxE) · [Урок №1 основы — PROZHEKTOR8KVT](https://www.youtube.com/watch?v=zcGwsCN5h0E)

КОМПАС моделирует «от поверхности» (не из воздуха). Документы: **деталь / сборка / чертёж**.

### E. КОМПАС — 2D-чертёж и оформление по ЕСКД

- **Чертёж** (рамка А4 + штамп) vs **фрагмент** (пустое поле без рамки).
- **Геометрия:** окружность, многоугольник (вписанный/описанный — для шестигранника), вспомогательные прямые, **стили линий** (основная/осевая/тонкая), усечь кривую.
- **Копия по окружности** — массив отверстий по центру; **обозначение центра/осей**.
- **Менеджер документа:** управление листами (формат А4/А3/А2, ориентация **по ГОСТ** — А4 горизонтально гост не предусматривает), видами, слоями; добавить/удалить лист; **стиль оформления** (ГОСТ 2.104, первый/последующие листы).

- **Ассоциативный чертёж с 3D-модели:** «создать чертёж по модели»; вид модели (сверху/изометрия) + масштаб; **местный разрез** (замкнутый сплайн); вспомогательные виды (стрелка взгляда, разрыв проекционной связи, поворот вида). **АВТО-перестроение: правишь 3D → чертёж обновляется сам** (live-связь модель↔чертёж).
- **Образмеривание:** авто-размер, линейный/диаметральный/радиальный; **допуски/квалитеты** (h14/H14, система вала vs отверстия), шероховатость (Ra, классы), резьба (M110×4), допуски формы/база, технические требования.

### → Что забрать в DOLG (CAD)
Привязка к нашему [апгрейду CAD](../memory) и [тулбару](../memory):

- **Массивы** — прямоугольный/круговой/по траектории + ассоциативность («правишь источник → меняются все»): наш gap «Массив».

- **Слои** — цвет/тип/вкл-выкл/заморозка как организующий слой редактирования.
- **Привязки** (osnap) + орто + полярное отслеживание + динамический ввод — UX-минимум «как в AutoCAD».
- **ЕСКД-оформление** (штамп, форматы/листы по ГОСТ, стили линий, допуски/шероховатость) — у нас уже есть «Шаблоны ГОСТ», углубить.
- **Ассоциативность модель↔чертёж (КОМПАС)** — концептуально совпадает с нашей идеей [авто-реактивной схемы](../memory): правка геометрии → авто-пересчёт/перестроение зависимых представлений.
- **Тулбар:** видео показывают компактные ленты/контекстные вкладки (массив/блок дают контекстную вкладку при выделении) — образец для нашей оптимизации тулбара (ribbon + контекст вместо 6 рядов).

### 5. DevOps Roadmap 2026
[видео, 35:50](https://www.youtube.com/watch?v=a68hSZz0gAQ)

**TL;DR:** практичный DevOps-путь строится не от абстрактного списка технологий, а от рабочих задач:
версионировать конфиги, жить в Linux, понимать процессы/ресурсы/сеть, упаковывать приложения в Docker,
собирать CI/CD, затем переходить к Ansible, Kubernetes, мониторингу, логам и IaC.

**Порядок обучения из видео:**
- **Git** — начинать с него, потому что конфиги, pipeline, манифесты и документация тоже код.
- **Linux** — не просто читать, а жить в системе: терминал, файлы, права, редактор, сервисы.
- **Processes** — `ps`, PID, signals, zombie/orphan, `systemd`, unit-файлы, OOM killer, `/proc`.
- **Resource monitoring** — `top`/`htop`, load average, CPU, memory, `iowait`.
- **Disk** — `df`, `du`, inode exhaustion, ротация логов, поиск раздувшихся файлов.
- **Networking** — базовые модели, порты, DNS, маршрутизация, firewall; без этого Docker/K8s становятся магией.
- **Docker** — image/container, Dockerfile, volumes, networks, compose, registry, healthcheck.
- **CI/CD** — идеального pipeline нет: зависит от проекта, ветвления, окружений, тестов, релизной стратегии.
- **Ansible / IaC** — конфигурация серверов через idempotent playbooks, inventory, roles.
- **Kubernetes** — control plane, worker node, pod, deployment, statefulset, daemonset, jobs, configmap/secret,
  probes, requests/limits, services, ingress, PV/PVC, Helm.
- **Monitoring/logging** — Prometheus/Grafana, exporters, PromQL, dashboards, alerting; для логов ELK/OpenSearch или Loki.
- **Clouds/Terraform** — в конце, когда уже понятны Linux/Docker/CI/K8s; state хранить удалённо, например в S3.

- Уже закрыто: Git/Markdown как рабочая дисциплина, Dockerfile, Compose, `web/asgi/worker`, Redis,

## Видео-конспекты: симуляция и инженерная глубина (лекции)

### G. Как устроен SPICE изнутри
[Adi Teman — Behind the Scenes of the SPICE Circuit Simulator, Part 1 (18:06)](https://www.youtube.com/watch?v=1ZhzhWAt7xc)

Цель — из «SPICE-monkey» (тык-параметры-надеюсь) в proactive-инженера, понимающего, что под капотом.
- **История:** Berkeley SPICE 1972 (Nagle, ментор Pederson), public domain → захватил мир; потомки HSPICE/PSpice/Spectre.
- **Вход симулятора:** netlist (компоненты + связность) + device models + параметры + initial conditions + stimulus.
- **Ядро:** законы Кирхгофа (KCL/KVL) → система ОДУ → решается через **Modified Nodal Analysis (MNA)**. Для R/C/I: `i(v) + d/dt·q(v) + u(t) = 0`.
- **Типы анализа:** **DC** (рабочая точка: нелинейная система → линеаризация + **метод Ньютона** → «convergence»); **Transient** (дискретизация времени: на каждом шаге — DC с начальными условиями); **AC** (DC-точка + линеаризация для малого сигнала).
- → **DOLG:** подтверждает архитектуру нашего `monte_carlo.solve_dc` (это и есть MNA). Точки роста без новых сущностей: нелинейные элементы (диод/LED/транзистор) через Ньютона-Рафсона; transient как цепочка DC-шагов; диагностика «convergence» в ответах AI (почему схема не решается).

### H. Monte Carlo по-научному
[MIT OpenCourseWare 6.0002 — Lecture 6. Monte Carlo Simulation (50:05), J. Guttag](https://www.youtube.com/watch?v=OgO1gpXSUzU)

- **MC** = оценка неизвестной величины через инференциальную статистику: популяция → **случайная** выборка → вывод (случайность критична).
- **Закон больших чисел** (Бернулли): больше испытаний → ближе к истинной величине.
- Ошибки интуиции: **gambler's fallacy** (не «выровняется») vs **regression to the mean** (после экстремума следующее ближе к среднему — события независимы).
- **Дисперсия/СКО:** чем больше разброс, тем больше выборка нужна для той же уверенности; СКО бессмысленно без среднего.
- **Доверительный интервал** (эмпирическое правило для нормального распределения): 68% в ±1σ, 95% в ±1.96σ, 99.7% в ±3σ. Допущения: нет смещения + нормальность ошибок.
- → **DOLG:** теория под наш `run_tolerance_analysis`. Точки роста: возвращать не только worst-case, а **среднее ± 95% CI** по узлам; показывать **СКО как метрику риска**; **адаптивно** наращивать N итераций пока CI не сузится (вместо фикс. 2000); честно сообщать «нужно больше итераций». Прямое усиление существующего MC-движка + L1/L2 toolkit.

### I. Земля в платах / целостность сигналов
[Рик Хартли (пер. Dmitry Muravyev) — «Земля в печатных платах» (2:01:30)](https://www.youtube.com/watch?v=c-VAPqNBDRU)

- **Энергия передаётся в диэлектрике** (ЭМ-поле между проводником и опорной плоскостью), не «внутри меди» — медь лишь направляет поле.
- **«Земля» = возвратный путь сигнала**, не «слив в грунт». Заземление на грунт — ТОЛЬКО безопасность, к ЭМС отношения не имеет (телефон/авионика проходят ЭМС без заземления).
- **Возвратный ток на ВЧ течёт прямо под дорожкой** (путь наименьшей индуктивности/импеданса); на НЧ — растекается (наименьшее сопротивление). → под сигналом нужна **сплошная опорная плоскость**.
- **Не разрезать опорную плоскость под сигналами:** разрыв → большая петля возвратного тока → излучение (EMI) + перекрёстные помехи. Не вести сигнал через зазоры/разрезы плоскости.
- **Дорожку держать близко к опорной плоскости** (тонкий диэлектрик) → малая петля, низкая индуктивность, меньше помех.
- **Стек слоёв:** смежность «сигнал-земля»; при переходе сигнала между слоями — **возвратное переходное (stitching via) рядом**; секции (аналог/цифра/ВЧ) разделять **размещением**, а не разрезанием единой земли.
- → **DOLG (PCB-editor/DRC/автороутер):** новые проверки без новых сущностей — (1) сигнал не пересекает разрыв опорной плоскости; (2) у высокоскоростного сигнала есть сплошная земля под ним; (3) рядом с сигнальным via — возвратное via; (4) совет по стеку (сигнал-земля смежно). Автороутер: штраф за петлю/пересечение зазора (как уже штрафуем повороты в A*-роутере).

### L. PCB-роутинг ≠ симуляция/схема — другие правила (важно)
Веб-материалы: [Altium: 45° vs 90° angle myths](https://resources.altium.com/p/pcb-routing-angle-myths-45-degree-angle-versus-90-degree-angle) · [NextPCB: Ultimate PCB Routing Guide](https://www.nextpcb.com/blog/pcb-routing) · [AllPCB: Trace Routing Design Rules](https://www.allpcb.com/allelectrohub/pcb-trace-routing-design-rules-best-practices-for-manufacturability) · [Schemalyzer: 25 PCB layout rules](https://www.schemalyzer.com/en/blog/pcb-design/best-practices/pcb-layout-best-practices) · [pcbrunner: routing design rules](https://www.pcbrunner.com/a-complete-guide-to-pcb-routing-design-rules-and-best-practices-for-success/)

**Главное отличие от схемы/симуляции:** в схеме провод — это *логическая* связь (можно под прямым углом, длина/форма не важны). На **плате дорожка — физический проводник**, и форма влияет на ЭМС, импеданс, технологичность. Правила «совершенно другие»:
- **Углы: НЕ прямые (90°).** Острый угол даёт отражения/ЭМС и «acid trap» при травлении. Правило: **два изгиба по 45°** вместо одного 90°; для высокоскоростных — **скруглённые дуги** (гладкий импеданс). На схеме 90° — норма, на плате — антипаттерн.
- **Ширина дорожки** — не косметика: задаёт **ток** (нагрев по IPC-2221) и **импеданс**. Питание/земля — широкие/полигоны; сигналы — под целевой импеданс. В схеме у «провода» ширины нет вообще.
- **Зазор (clearance)** между дорожками/паями ≥ правил завода (≈10–15 mil) — против кросстолка и под технологию. В схеме зазора нет.
- **Vias** — переходы между слоями: минимизировать (паразитная L/C, точки отказа), не ставить на высокоскоростных/импедансных; via в землю — для экранирования. На схеме слоёв нет.
- **Сплошной полигон земли** — низкоимпедансный обратный путь; **нельзя вести сигнал над разрывом земли** (петля = антенна = №1 причина ЭМС-провалов). В симуляции «земля» — один узел `0`, без геометрии.
- → **DOLG (вывод для A*-автотрассировщика):** наш A* по сетке 0,5 мм со штрафом за поворот даёт **манхэттен (90°)** — это против правил PCB. Апгрейд: (1) **октилинейный роутинг** (разрешить ходы по диагонали → 45°) ИЛИ пост-обработка: каждый 90°-угол → срезать двумя 45° (chamfer) / дугой; (2) ширина дорожки из тока цепи (питание шире); (3) clearance-проверка как hard-constraint; (4) полигон земли как заливка с проверкой «нет сигнала над разрывом». Это переводит автотрассировку из «учебной» в «по правилам отрасли» — отдельный трек после клиентского движка.

### M. Максимизация клиентского движка DOLG (анализ + рычаги)
Цель (запрос юзера): докрутить **клиентский** движок до максимума. **Сервер обязателен** (архитектурно — серверный масштаб на Xyce/Celery, см. план защиты; это пост-защита), но **до защиты демонстрируем именно на клиентском движке** — поэтому всё, что можно, гоняем в браузере и доводим до предела. Текущий стек: `ngspice.wasm` + Web Worker (`ngspice-worker.js`), JS-MNA fallback, Canvas2D↔Pixi(WebGL) авто-переключение, Three.js (r140) для 3D, Monte-Carlo (сейчас на сервере, NumPy).

**Рычаги по слоям:**
- **Вычисления (SPICE):** ngspice уже в воркере — не блокирует UI. Максимум: (1) **WASM SIMD** (если сборка ngspice поддерживает) + **pthreads/SharedArrayBuffer** — но требует HTTP-заголовков **COOP/COEP** (`Cross-Origin-Opener/Embedder-Policy`), это серверный gotcha, проверить middleware; (2) **transferable ArrayBuffer** для результатов (узлы/токи) вместо JSON-сериализации больших массивов — меньше GC, быстрее воркер→main; (3) переиспользовать загруженный WASM-инстанс между прогонами (не реинициализировать).
- **Monte-Carlo на клиенте:** сейчас сервер (NumPy). Рычаг — **worker-pool** (N воркеров = N ядер) гоняют MNA-итерации параллельно в браузере → «комбайн» без сервера для статистики; CPU-bound, корутины не помогут, нужны именно воркеры.
- **2D-рендер:** Canvas2D↔Pixi есть. Максимум: **OffscreenCanvas** (рендер в воркере, main-поток свободен), **dirty-rect** перерисовка (не весь кадр), батчинг спрайтов в Pixi, авто-выбор рендера по FPS (см. конспект защиты §5).
- **3D-рендер (Three.js):** для больших плат — **InstancedMesh** на повторяющиеся корпуса (один draw call на тип), **merge geometry**, **frustum culling/LOD**, переиспользование shared-материалов (уже частично). Дальше — апгрейд **r140 → r160+** ради **WebGPURenderer** (на порядок больше объектов), но это крупный апгрейд (API-сдвиги) → post-defense.
- **Загрузка/архитектура:** `simulation.html` ~14k строк блокирует парс/кэш. Рычаг (post-defense) — **split на ES-модули** + ленивая загрузка тяжёлых частей (3D/Pixi по требованию, не на каждый вход).
- **Приоритет для движка:** (1) probes/RF/measurements — точность и охват анализов (done RF+probes); (2) transferable-буферы + reuse WASM (дёшево, заметно); (3) client-side MC worker-pool (снимает зависимость от сервера); (4) InstancedMesh для 3D; (5) OffscreenCanvas; (6) WebGPU/модули — post-defense.

> Связка с другими конспектами: серверный масштаб — Xyce (§ план защиты), но **клиентский максимум** — это воркеры + WASM-threads + GPU-инстансинг, всё в браузере.

### N. [Видео] Altium Academy — «Top 5 Beginner PCB Design Mistakes» (Phil Salmony, 12:51)
Источник: <https://www.youtube.com/watch?v=D0X76Kbf8fQ> (транскрипт снят через scripts/yt_transcript.py). Конкретные инженерные правила PCB-роутинга с цифрами — прямо питают наш DRC/автотрассировщик (дополняет §L).

- **1. Trace spacing (зазор) — главная ошибка новичков.** Не лепить дорожки по минимальному зазору завода: (а) низкий выход годных у предела техпроцесса, (б) кросстолк между параллельными дорожками. Правило: **clearance ≥ 3× толщины диэлектрика** к соседнему слою (пример: диэлектрик 0,1 мм → зазор ≥ 0,3 мм; в проекте делали 0,6 мм). Параллельные участки — как можно короче. «Есть место — используй его».
- **2. Trace width — НЕ одинаковая для всего.** Высокоомные/чувствительные сигналы (вход АЦП) — **тоньше** (меньше связь/ёмкость), напр. 0,2 мм; питание — **шире** (ток/нагрев), напр. 0,5 мм несёт >1,5 А. Считать ток дорожки по IPC (инструмент Saturn PCB Toolkit). Импедансные дорожки — отдельная тема.
- **3. Via sizing.** Кольцо (annular ring) = (диаметр пада − отверстие)/2; **≥ 0,15 мм** как правило. Дефолты: 0,7 мм пад / 0,3 мм сверло; мелкие 0,5/0,2. Одна via несёт **~1–2 А** → отсюда число via для питания. Антипаттерн: большое сверло + крошечный пад (тонкое кольцо).
- **4. Decoupling.** Конденсатор развязки — **максимально близко к питающим пинам IC** (минимизировать индуктивность дорожек); via в внутренние power/GND-плоскости рядом с пинами; толстые короткие дорожки кап→via. Дистанция ~2 мм.
- **5. Reference/ground plane.** Сигнал всегда идёт **над сплошной опорной плоскостью** (обычно GND); **нельзя пересекать разрыв/вырез плоскости** (via чужой цепи режет полигон → петля). Нужна земля и **под** дорожкой, и **по бокам** (поля расходятся, не только вниз).
- → **DOLG (DRC-правила к реализации, клиентский движок):** добавить проверки/подсказки: (1) clearance ≥ 3× диэлектрика (не только минимум завода); (2) ширина дорожки из тока цепи (питание шире сигналов); (3) annular ring ≥ 0,15 мм; (4) близость decoupling-капа к пинам IC; (5) «сигнал над разрывом полигона земли» — флаг. Это ровно тот класс правил, что у нас уже есть для схемы (ERC) — расширяем на PCB-слой. Считать ток/импеданс можно прямо в браузере (формулы IPC-2221), без сервера.

### O. [Видео] Hans Rosenberg — «Flawless PCB design: 3 simple rules» (заземление, 11:04)
Источник: <https://www.youtube.com/watch?v=xhuHAhIKWoM> (транскрипт через scripts/yt_transcript.py). 30 лет опыта; на тест-плате (фильтр 9-го порядка, 30 МГц) показано, как разводка земли меняет АЧХ от «худшей» до «идеальной».

- **3 правила заземления (итог):** (1) **сплошной полигон земли без разрывов**; (2) **у каждого соединения с землёй своя via**, максимально близко к паю компонента; (3) **4-слойный стек** (земля близко к сигналу).
- **Почему 4 слоя:** индуктивность via резко зависит от длины/стека. 2 слоя (1,6 мм) → via ~500 нГн; 4 слоя (земля на сл.2, ~0,2 мм) → ~12–47 нГн. На 800 МГц подавление: 2 слоя −22 дБ vs 4 слоя −58 дБ (×50). Тонкие земляные дорожки = плохая земля + кросстолк (токи земли суммируются).
- **Обратный ток идёт под сигнальной дорожкой** (петля) → площадь петли критична; разные петли могут вести себя как **связанные индуктивности (трансформатор)**.
- **Связь катушек:** два индуктора рядом наводятся друг на друга → разнести и **повернуть на 90°** (поля не пересекаются). Так же развязывают токовые петли.
- → **DOLG (выводы):** (а) усиливает §N-правило «сигнал над сплошной землёй, не над разрывом»; (б) DRC-хинт «каждая земля → своя via у пая»; (в) хинт «индукторы рядом — разнести/повернуть 90°»; (г) **обучающий контент**: показать в симуляторе/обучении связь «разводка земли → АЧХ» (у нас есть и АЧХ через RF-движок, и понятие петли) — сильная связка sim↔layout для тренажёра. Большинство правил — физика ЭМС (площадь петли, индуктивность via), их можно подавать как **подсказки/уроки**, не обязательно автоматизировать в 2D-роутере.

### W. [Видео·бэклог] «Gauss-Newton / Non-Linear Least Squares» (Meerkat Statistics, 20:02)
Источник: <https://www.youtube.com/watch?v=Kln0ZQ7sX8k> (транскрипт через scripts/yt_transcript.py). Из VIDEO_BACKLOG (численные методы → нелинейный солвер диод/LED).

Это ровно метод из видео, применённый к уравнениям цепи. Практика: **демпфирование шага** напряжения (диод экспоненциальный — иначе расходится), лимит итераций, допуск. ### AC. [Текст] Транзиентный анализ — companion-модели C/L (численное интегрирование)
Источники: [Qucs: Energy-storage components](https://qucs.sourceforge.net/tech/node26.html) · [Purdue: Numerical Integration Techniques (PDF)](https://docs.lib.purdue.edu/cgi/viewcontent.cgi?article=1301&context=ecetr) · [IISc: Basics of SPICE, Lecture 4+5 (PDF)](https://ece.iisc.ac.in/~dipanjan/E8_262/E8262-CAD_4+5.pdf) · [Cheng: Life of SPICE as transient simulator (PDF)](https://cseweb.ucsd.edu/~kuan/talk/mtu18/MtuTalk022318.pdf). ### AD. [Текст] Алгоритмы автотрассировки PCB (теория + реализация)
Источники: [Maze Router: Collected Techniques (PDF)](https://www.academia.edu/69808970/Maze_Router_Collected_Techniques) · [The Mathematics of PCB Trace Routing](https://tinycomputers.io/posts/the-mathematics-of-pcb-trace-routing.html) · [Freerouting (gridless, expansion rooms)](https://github.com/freerouting/freerouting) · [VLSI obstacle-avoiding global routing (arXiv)](https://arxiv.org/pdf/2503.07268).

- **Lee maze (1961):** BFS по сетке, **гарантирует кратчайший путь**, но медленный и прожорлив по памяти.
- **A\* с эвристикой:** направленный поиск — быстрее (наш autorouter — это A* по сетке 0,5 мм + штраф за поворот, greedy: короткие нети первыми). **Line-search** ускоряет ещё (×29–93 над Lee, ×5–19 над A*).
- **Gridless (Freerouting):** НЕ дискретизирует плату в сетку, а работает на **непрерывной плоскости**, разбитой на выпуклые полигоны («expansion rooms») → **произвольные углы (в т.ч. 45°)** и лучшее качество. Это «правильный» путь к красивым трассам, но крупный переписыватель.
- **Rip-up & reroute:** итеративно — развести, найти конфликты, **«сорвать» мешающие трассы и переразвести**; мультислой, мульти-терминальные нети. Резко поднимает % разведённых.
- → **DOLG (по плану):** (1) наш A* greedy без rip-up → у `autoroute_stats` есть `failed`/`unreachable`; **добавить rip-up-reroute** = меньше неразведённых (качество за умеренный код); (2) **45° дёшево:** либо 8-связные соседи в A* (диагонали), либо пост-обработка 90°→два 45°/дуга (наш §L) — без перехода в gridless; (3) gridless/expansion-rooms — «как Freerouting», но это **post-defense** (большой рефактор); (4) line-search — если A* станет узким местом. Для вау к защите хватит **45°-пост-обработки + rip-up**: трассы станут «как настоящие», риск умеренный, autorouter трогаем точечно.

### AE. [Текст] Архитектура EDA-флоу: схема → нетлист → PCB → 3D (как у KiCad)
Источники: [KiCad: schematic → PCB (RayPCB)](https://www.raypcb.com/kicad-schematic-to-pcb/) · [KiCad PCB Editor docs](https://docs.kicad.org/9.0/en/pcbnew/pcbnew.html) · [KiCad Schematic Editor docs](https://docs.kicad.org/9.0/en/eeschema/eeschema.html) · [Hussam: KiCad schematic capture](https://hussamtalkstech.com/introkicadp1/).

- **Канонический EDA-флоу (KiCad):** (1) **schematic capture** — символы + нети; (2) **annotation** — рефдезы (R1, C1…) автоматически; (3) **netlist** — файл связности (что с чем соединено); (4) **footprint association** — каждому символу сопоставляется физический футпринт; (5) **PCB layout** — нетлист импортируется в плату → расстановка + трассировка; (6) **Gerber** + **3D**.
- **Нетлист = единый мост:** PCB-редактор общается со schematic-редактором **через связность** (в KiCad — напрямую, без промежуточных файлов, либо импорт netlist). **Forward annotation:** правки схемы прокидываются на плату.
- → **DOLG (наш флоу зеркалит KiCad — подтверждение архитектуры):** schematic editor → `scheme_data` (**components + connections = нетлист**) → `compute_pcb_layout` (футпринт через `footprintForComponent` + авто-расстановка) → `autoroute_layout(scheme_connections)` → 3D + Gerber. То есть **`scheme_connections` — наш единый «нетлист-мост»**, ровно идея «реюз спайси для роутинга»: одна связность кормит и симуляцию, и плату.
- **Где мы проще KiCad (и куда полировать):** (а) **footprint association неявная** (из type/package) — KiCad даёт явный редактируемый маппинг символ↔футпринт (можно добавить выбор корпуса в UI); (б) **forward annotation** — при правке схемы переразложить/перетрассировать (наш «один клик» из плана = упрощённый forward annotation); (в) annotation рефдезов — у нас есть label'ы. **Вывод:** архитектурно DOLG = мини-KiCad в браузере; нетлист уже единый мост — надо лишь сделать переход «схема→плата→3D» бесшовным и красивым (план), не меняя архитектуру.

### AF. [Текст] Реализация: реалистичный 3D-борд (PBR в Three.js)
Источники: [PBR в Three.js (Medium)](https://medium.com/@Makoto_29712/experimenting-with-pbr-textures-usingthree-js-a25aad28ed65) · [three.js MeshStandardMaterial docs](https://threejs.org/docs/api/en/materials/MeshStandardMaterial) · [discoverthreejs: PBR & Lighting](https://discoverthreejs.com/book/first-steps/physically-based-rendering/) · [Render PCB in 3D (Medium)](https://medium.com/@hemalchevli/render-pcb-in-3d-889b62899bc7).

- **PBR-материалы:** `MeshStandardMaterial` (база: baseColor/metalness/roughness) и `MeshPhysicalMaterial` (доп.: clearcoat и т.п.). PBR = физически корректная реакция на свет «при любом освещении», без ручной подгонки.
- **Карты:** albedo/normal/roughness/metalness/displacement; **environment map** — ключ: без неё металл/золото **не отражают** и выглядят плоско; с env-map (HDR/equirect) появляются корректные блики.
- **Слои реальной платы:** FR-4 подложка → медь (высокий metalness) → soldermask (полуглянец, semi-gloss) → silkscreen (матовый белый) → ENIG-пады (золото, металлик). Normal-map на маске даёт фактуру.
- → **DOLG (у нас палитра уже есть — `scheme-3d-materials.js`: pcbGreen/copperTop/pad-ENIG/silkscreen/metalCan/epoxy):** реализация «как настоящая» = (1) **🟢 добавить environment map на сцену** → все наши PBR-материалы (металл/ENIG/медь/эпокси) сразу заиграют отражениями — **самый дешёвый и сильный шаг** (подтверждает §P #1; материалы готовы, не хватает только env-map); (2) **дорожки с толщиной** (сейчас плоские) — тонкий extrude + `copperTop`; soldermask поверх; (3) опц. `MeshPhysicalMaterial` **clearcoat** для глянца маски; (4) опц. normal-map на soldermask для фактуры. **Главное:** мы уже на `MeshStandardMaterial` с разумными metalness/roughness → не хватает **одного env-map**, чтобы скакнуть в «реалистично». Это клиент, изолировано в 3D-оверлее, проверяемо headless-скрином.

**Итог исследования пайплайна (§AD–§AF):** теория роутинга (Lee→A*→gridless+rip-up), архитектура (EDA-флоу, нетлист=мост, DOLG≈мини-KiCad), реализация (PBR+env-map). Всё подтверждает план: пайплайн собран → полируем визуал. Самые дешёвые скачки «как настоящее»: **env-map (3D)** + **45°-трассы/rip-up (роутер)** + **один клик (флоу)**.

- **Флоу:** Schematic → assign footprints → PCB editor (**нетлист переносится автоматически** при открытии PCB; компоненты «кучей» + **ratsnest** — тонкие линии «что соединить») → расстановка → трассировка → **DRC** → Gerber → заказ (JLCPCB).
- **3D:** быстрый **3D-вид платы + экспорт STEP**, **мгновенное обновление 3D после любой правки PCB**, «vivid mechanical presentation». ← Это в точности твоя вау-идея «красиво в 3D, как настоящая», и она **доказанно реализуема в браузере**.
- → **DOLG (валидация + позиционирование):** EasyEDA подтверждает (1) сам концепт DOLG (браузер: схема+симуляция+PCB+3D — жизнеспособно), (2) **вау-вектор «мгновенный реалистичный 3D из PCB»** реален в вебе. **Дифференциаторы DOLG для защиты:** интегрированный **магазин компонентов (BOM→купить)**, **AI-ассистент**, обучение — то, чего у EasyEDA нет. Флоу EasyEDA (нетлист-автоперенос → ratsnest → route → DRC → 3D → Gerber) **зеркалит наш** (§AE) — наша авто-расстановка даже удобнее «кучи». STEP-экспорт — наш пост-защита MCAD (§X). Тезис защиты: **«DOLG — браузерный ECAD уровня EasyEDA, но с магазином + AI + обучением»**.

### AH. [Текст] RAG-грудинг, цитирование, борьба с галлюцинациями → усиление ассистента
Источники: [Pinecone: RAG](https://www.pinecone.io/learn/retrieval-augmented-generation/) · [RAG Grounding: fake citations (Medium)](https://medium.com/@Nexumo_/rag-grounding-11-tests-that-expose-fake-citations-30d84140831a) · [Production RAG: chunking/retrieval/eval (Towards AI)](https://towardsai.net/p/machine-learning/production-rag-the-chunking-retrieval-and-evaluation-strategies-that-actually-work) · [Chunking strategies 2026 (Firecrawl)](https://www.firecrawl.dev/blog/best-chunking-strategies-rag). Под усиление `ai_retrieval`/ассистента.

- **RAG = грудинг ответа на внешних фактах + цитаты** для проверки человеком. Снижает галлюцинации.
- **Citation-shaped hallucinations:** цитаты НЕ гарантируют верность — retrieval мог подтянуть «рядом лежащее», ранкер предпочёл keyword-overlap семантике, генератор «склеил» логику. → нужна **качественная выборка + проверка claim против источника**.
- **Чанкинг:** адаптивный/семантический (по логическим границам) >> фиксированный (в одном клин-исследовании 87% vs 13%). Фикс-размер рвёт мысль. Для длинных многотемных доков — обязателен.
- **Длина контекста:** крупные чанки (1024+ токенов) для полноты, но «context cliff» ~2500 токенов — дальше качество падает → не перегружать.
- **Reranking:** cross-encoder уточняет кандидатов после первичной выборки; продакшн = **hybrid (vector + BM25) → rerank → context**.
- → **DOLG (усиление ассистента):** (1) **наш ассистент во многом НЕ-LLM** — числа из движков (compute-don't-guess, «источник: MNA…»), правила, глоссарий → **галлюцинаций по числам почти нет by design** (сильный тезис защиты против «это ChatGPT придумал»); citation-hallucination риск — только в Claude-chat-пути с глоссарий-грудингом; (2) `ai_retrieval` сейчас substring/TF-IDF → улучшить: **семантический чанкинг статей знаний** (не фикс-размер), **hybrid (TF-IDF + ключевые слова)**, не перегружать контекст (cliff); (3) **reranker** = Phase C нашего rag_roadmap (cross-encoder поверх кандидатов); (4) **проверка цитат**: expert-first уже метит «источник:» у чисел — распространить на статейные цитаты (показывать, откуда факт). Вывод: усиление = качество retrieval (чанкинг+hybrid+rerank) + сохранять «число только из движка».

### AI. [Текст] Агентные паттерны: ReAct / Tool-calling / Plan-then-Execute → мощное усиление ассистента
Источники: [Tool-calling vs ReAct agents (Medium)](https://medium.com/@dzianisv/vibe-engineering-langchains-tool-calling-agent-vs-react-agent-and-modern-llm-agent-architectures-bdd480347692) · [ReAct vs CodeAct (Medium)](https://medium.com/@siddhuajay001/react-vs-codeact-architecting-the-next-generation-of-agentic-llm-systems-80af42684727) · [Agentic AI: architectures & taxonomies (arXiv)](https://arxiv.org/pdf/2601.12560) · [AgentScope 1.0 (arXiv)](https://arxiv.org/pdf/2508.16279).

- **ReAct:** чередует рассуждение (CoT) и действие (вызов инструмента) в цикле; текстом, парсится, **трассируемо** (видно ход мысли).
- **Tool-calling:** модель выдаёт **структурный JSON-вызов функции**; быстрее/надёжнее на простых задачах (часто fine-tuned).
- **Plan-then-Execute (тренд 2025):** LLM сначала строит **многошаговый план**, затем **отдельный исполнитель** выполняет шаги — причём исполнителем могут быть **дешёвые модели ИЛИ прямые не-LLM вызовы функций** → резко меньше обращений к большой модели.
- 2025: агентность, **параллельные вызовы инструментов**, async.
- → **DOLG (мощное усиление — блюпринт):** наш `rule_ai` сейчас = **статический маппинг intent→секции**. Апгрейд до **Plan-then-Execute оркестратора** над реестром `ai_algorithms`: (1) **планировщик** (правила/эвристика/опц. локальная модель) по запросу строит план — какие движки и в каком порядке (часто несколько intent'ов сразу: «проверь LED-цепь» → план `[dc_voltages, led_current, derating, drc]`); (2) **исполнитель = наш реестр движков** — это ровно «не-LLM прямые вызовы функций» из паттерна (детерминированно, дёшево, self-hosted); (3) **ReAct-трассируемость:** показывать план как шаги («считаю напряжения → ток LED → запас мощности → DRC») — прозрачно и **анти-галлюцинация** (каждый шаг = реальный движок, §AH); (4) **параллельный запуск** независимых движков (через воркеры, §Q). Это превращает ассистента из «шаблон по intent» в **агента, который сам собирает многодвижковый проверяемый ответ** — мощный и защищаемый скачок, без внешней LLM. Каркас уже есть: `Algorithm{key,title,intents,run}` = готовое описание «инструмента»; нужен слой-планировщик поверх `sections_for_intent`.

### AK. [Видео·бэклог] «Stop Oversizing MOSFETs» (High SNR, 13:05) → derating-движок + real-модели
Источник: <https://www.youtube.com/watch?v=dqgPj5GjbJk> (транскрипт через scripts/yt_transcript.py, YouTube снова доступен). Обогащает мой новый `derating`-движок и ветку «реальных» моделей.

- **Перезавышать номинал по напряжению — вредно:** выше breakdown-V → толще drift-регион → **RDS(on) растёт как ~V_bd^(2…2.5)** («кремниевый предел») → больше нагрев (поменяли отказ по напряжению на тепловой); крупнее кристалл → паразитные ёмкости ↑ → динамические потери.
- **Derating factor** = % от абсолютного макс., который реально испытывает компонент. По отраслям: **промышленные приводы 50%** (номинал ×2, IEC, переживают регенеративное торможение 540→800-900В → детали 1200В); **high-density DC-DC/телеком 80%** (margin 20%, IPC-9592B — нельзя завышать, расплавит плату); **аэрокосмос/NASA ≤75%** (космические лучи, single-event burnout).
- **Анатомия выброса:** `V_peak = V_supply + L_параз·di/dt` (back-EMF от индуктивности петли). Лечить **в источнике:** gate-резистор (медленнее di/dt), RC-снаббер, active clamp — НЕ завышением номинала. (Связь с §O/§N: петля/индуктивность.)
- → **DOLG:** (1) **обогащает `derating`-движок** ([[local-ai-toolkit]]): ввести **derating-factor** и доменные пороги (50/75/80%) вместо фикс. 50/100% — вердикт точнее, цитируемо по IEC/IPC/NASA; (2) можно добавить **derating по напряжению** (V против V_max), не только по мощности; (3) ветка **«реальных» моделей** ([[model-library-ideal-real]]): RDS(on)↔V_bd-tradeoff — характерная «реальная» деталь MOSFET; (4) expert-правило-хинт «не завышай номинал — подавляй выброс gate-R/снаббером/clamp». Всё клиентски (формулы/правила).

### AL. [Видео·бэклог] «Компенсационные стабилизаторы напряжения» (Dmitry Kuznetsov, 20:17)
Источник: <https://www.youtube.com/watch?v=c2ctYvsGB-g> (транскрипт через scripts/yt_transcript.py). Питает сценарий ассистента «собери стабилизатор 5В» + expert-правила.

- **Компенсационный (линейный) стабилизатор = следящая система:** регулирующий элемент (силовой транзистор) + источник опорного (Vref) + усилитель ошибки; держит Vout постоянным, меняя падение на проходном транзисторе. Выше коэффициент стабилизации и токи, чем у параметрического (стабилитрон). Усилитель ошибки + делитель с выхода ↑ коэффициент стабилизации.
- **Интегральные:** **78xx** (+) / **79xx** (−), сов. **КР142ЕН** («Кренки»). ### AO. [Видео·бэклог] «Theoretical Foundations of GNN» (Petar Veličković, 1:12:20)
Источник: <https://www.youtube.com/watch?v=uF53xsT7mjc> (главы+интро через scripts/yt_transcript.py). Эталон теории GNN — под наш нейро-движок ([[gnn-block-a1]], §T).

- **Перестановочная инвариантность/эквивариантность (ядро):** порядок узлов произволен → выход GNN должен быть **инвариантен** (граф-уровень) или **эквивариантен** (узел-уровень) к перестановкам. Поэтому агрегатор соседей — **перестановочно-инвариантный** (sum/mean/max).
- **Message passing:** каждый узел агрегирует признаки соседей (инвариантный агрегатор) + update; больше слоёв → больше **рецептивное поле** (соседи соседей).
- **Выразительность ограничена тестом изоморфизма (1-WL):** GNN не сильнее 1-WL в различении графов → некоторые неизоморфные графы неразличимы.
- → **DOLG (нейро-движок §T):** (1) схема=граф (узлы=компоненты/цепи, рёбра=связи) — наша премиса верна; (2) **перестановочная инвариантность = почему GNN обобщается** на новые схемы независимо от порядка компонентов (ключ к генерализации предиктора напряжений); (3) агрегация соседей + слои = рецептивное поле — ровно наш GraphConv; нужно достаточно раундов message-passing, чтобы «увидеть» путь источник→узел; (4) **1-WL-предел = честный кавеат:** GNN может путать похожие топологии → поэтому GNN у нас **подсказка поверх проверяемого MNA, а не замена** (expert-first, §AI/§AH). Стек — PyTorch (уже есть). Инференс в браузере — ONNX (§AJ).
